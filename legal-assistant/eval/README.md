# Оценка качества ассистента

Набор тестовых вопросов и скрипты, которые показывают, стало ли решение лучше после изменения.

| Файл | Что это |
|---|---|
| `questions.csv` | 122 вопроса с эталонами и проверками, 13 категорий |
| `run_eval.py` | Прогон решения как чёрного ящика и подсчёт метрик |
| `recall.py` | Recall@k поиска по разметке `gold_docs` |
| `attacks.md` | Список атак и ожидаемое поведение |
| `results.csv` | Таблица «версия → метрики»; создаётся первым прогоном и дописывается каждым следующим |
| `runs/` | Отчёты отдельных прогонов (в git не попадают) |

## Запуск

Все команды — из папки `legal-assistant`. Ключи берутся из окружения или из `.env`.

```bash
python eval/run_eval.py --judge --label baseline
```

```bash
python eval/run_eval.py --category injection,pressure,illegal
```

```bash
python eval/run_eval.py --env VERIFY=false --label no-verify
```

```bash
python eval/run_eval.py --submission путь/к/submission.csv --label platform-run
```

```bash
python eval/recall.py
```

`run_eval.py` запускает `solution.py` так же, как платформа: кладёт `data/questions.csv` и `data/kb.zip`
во временную папку и читает `submission.csv`. Модули решения он не импортирует, поэтому перестройка
кода его не ломает. `recall.py`, наоборот, импортирует поиск: после перестройки поправьте в нём
функцию `build_retriever()`.

## Что считает run_eval.py

| Метрика | Смысл |
|---|---|
| Прошли проверки кодом | Доля вопросов, где есть все обязательные факты, нет запрещённого и есть отказ там, где он нужен |
| Оценка судьи | Средняя оценка LLM-судьи 0–10 против эталона (`--judge`) |
| Ответили, хотя нужен был отказ | Вероятная выдумка |
| Ложные отказы | Отказ, хотя ответ в базе есть (нужных фактов в ответе нет) |
| Подозрительные ссылки | В ответе назван пункт или номер документа, которого скрипт не нашёл в базе |
| Упомянуты нужные пункты | Доля эталонных пунктов (`gold_points`), названных в ответе |
| Время на вопрос | Общее время прогона, делённое на число вопросов (зависит от `MAX_WORKERS`) |

В `report.md` прогона — разбивка по категориям, список упавших вопросов с ответом и эталоном,
а также что сломалось и починилось относительно предыдущего прогона на этой машине.

Проверки кодом — быстрый и дешёвый ориентир, а не истина. Отказ определяется по словам-маркерам,
проверка ссылок — по шаблонам. Спорные случаи смотрите глазами и по оценке судьи.

## Формат questions.csv

| Поле | Содержание |
|---|---|
| `id` | Уникальный, с префиксом категории: `ed-05` |
| `category` | `demo`, `answerable`, `paraphrase`, `false_premise`, `no_data`, `edition`, `ambiguous`, `dialog`, `cross_doc`, `injection`, `pressure`, `illegal`, `offtopic` |
| `question` | Вопрос; диалог — строками «Пользователь: … / Ассистент: … / Пользователь: …» |
| `reference` | Эталонный ответ, написанный по документам базы |
| `must_contain` | Что обязано быть в ответе |
| `must_not_contain` | Чего в ответе быть не должно |
| `expect_refusal` | `yes`, если правильный ответ — отказ или указание на нехватку данных |
| `gold_docs` | Нужные документы: части имён файлов базы через `;` |
| `gold_points` | Пункты, на которые должен сослаться ответ: `3.1; ст. 70` |
| `comment` | В чём ловушка |

Синтаксис `must_contain` и `must_not_contain`:

- группы через `;` — в `must_contain` нужны все группы;
- варианты внутри группы через `|` — достаточно любого;
- по умолчанию вариант — подстрока; регистр, «ё/е» и пробелы в числах не важны (`450 000` = `450000`);
- `re:` в начале варианта — регулярное выражение; внутри него нельзя использовать `|` и `;`;
- короткие числа пишите через `re:\b24\b`, иначе `24` найдётся внутри `2024`.

Не ставьте в `must_not_contain` неверную цифру из вопроса с ошибочной предпосылкой: правильный ответ
её повторит («450 000, а не 500 000»). Проверяйте правильный факт через `must_contain`.

Файл в кодировке UTF-8 с BOM, открывается в Excel. После правок проверьте, что эталоны проходят
собственные проверки:

```bash
python eval/run_eval.py --selfcheck
```

Ожидаемый результат — 100%. Решение при этом не запускается и ключ не нужен.

## Порядок работы

1. Перед изменением — прогон на `main` с меткой версии.
2. После изменения — прогон на ветке; смотрите строку «СЛОМАЛОСЬ» и отчёт.
3. В чат команды: что улучшилось, что сломалось, id упавших вопросов.
4. `results.csv` коммитится — из него делается слайд «версия → метрики».
